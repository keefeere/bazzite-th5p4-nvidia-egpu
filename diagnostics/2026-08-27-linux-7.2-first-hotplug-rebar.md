# Linux 7.2 physical first-hotplug and dynamic ReBAR repair

## Scope

This note records the machine-specific experiment behind the guarded Linux
7.2+ first-hotplug path. It does not generalize the operation to other hosts,
enclosures or GPUs.

## USB4 host-router A/B

With `thunderbolt.host_reset=0`, a freshly powered TH5P4 repeatedly detected
both retimers but failed before PCI enumeration with `failed to reach state
TB_PORT_UP`. Removing only that argument and cold-booting the host left the
upstream kernel default (`host_reset=Y`) active. The next first hot-plug
enumerated the JHL9480 bridges, RTX VGA and RTX HDA functions in about one
second without a `TB_PORT_UP` failure.

The installer therefore retains `thunderbolt.host_reset=0` byte-for-byte on
the original pre-7.2 path and removes only its own copy on Linux 7.2+.

## Late PCI state

The successful physical hot-plug produced the exact configured topology and
bus ranges but left RTX BAR1 at 256 MiB. NVIDIA remained blocked. The device's
`resource1_resize` mask was `0000000000007fc0`, which includes ReBAR size code
14 (16 GiB).

The controlled transition validated that NVIDIA was absent, the HP Dock was
absent, the RTX functions were the only descendants of port `02:00.0`, the
other three TH5P4 ports were empty, and the root apertures still matched the
profile. It then ended the graphical session, unbound RTX HDA, removed only
the three empty ports and wrote size code 14 to `resource1_resize`.

Linux assigned:

- RTX BAR1: `0x800000000-0xbffffffff` (16 GiB);
- RTX BAR3: `0x7fe000000-0x7ffffffff` (32 MiB);
- root, upstream and RTX-bridge MMIO_PREF:
  `0x7fe000000-0xbffffffff` (16 GiB + 32 MiB).

This dynamic parent window is different from the large clean firmware window
but is complete, nested and non-overlapping. The verifier accepts it only when
the explicit dynamic-ReBAR marker or its private validation flag is present.

## Downstream quarantine

Linux distributed the remaining 16 KiB I/O aperture as 4 KiB to each empty
TH5P4 port. That is enough for the empty bridges but less than the 12 KiB
validated for the complete HP Dock PCI tree. Before NVIDIA binds, the repair
therefore unbinds only `0000:02:01.0:pcie204` from `pciehp` and records
`/run/egpu-pciehp-quarantined`.

The eGPU and USB tunnel remain available. PCIe/Ethernet hot-add through the HP
port is disabled until reboot. A normal early boot with the dock attached
restores the full reservation and does not apply this quarantine.

The first full-chain reboot initially looked like a timing boundary: the early
service's 5-second endpoint wait expired at `22:59:17`, and kernel PCI
enumeration started during that same second. Extending the guard to 12 seconds
made the same sequence repeat exactly at the new boundary and exposed the real
cause. The initramfs had enumerated a correct 16 GiB RTX BAR1, Linux 7.2's
upstream host reset then removed that PCIe tunnel, and the early service waited
for its replacement while its `Before=bolt.service` dependency prevented
`boltd` from authorizing it.

The service order is therefore version-aware. The proven legacy path remains
before `bolt.service`. Linux 7.2 and newer start and wait for `boltd` first,
then allow up to 12 seconds for the exact RTX endpoint before staging NVIDIA;
Cardwire and the display manager still start afterwards. The bounded wait is
used only after the exact TH5P4 router is visible, so an enclosure-absent boot
remains fast.

## Cold-attached HP Dock result

After fixing the service order, Linux 7.2 consistently exposed the complete
HP PCI tree and RTX before the graphical session, but RTX BAR1 could still be
only 256 MiB. Removing and rebuilding the HP subtree was not reliable with the
new allocator. The early compatibility path now validates that exact complete
dock tree, preserves its port, removes only the two known-empty TH5P4 siblings,
requests the 16 GiB RTX BAR1 through `resource1_resize`, restores the siblings
and runs the full dock/resource verifier before NVIDIA can bind.

The live validation passed at PCIe Gen4 x4 with the HP I225 Ethernet linked at
1 Gb/s and the configured StarTech DisplayLink adapter on a 5 Gb/s USB3
tunnel. This cold-attached path is the supported Linux 7.2 production flow.
The original pre-7.2 dock rebuild remains unchanged.

## Lifecycle boundary

Safe detach successfully ends the NVIDIA-first session, unloads the driver and
removes only the exact RTX branch. Once the USB4 cable is physically removed,
however, Linux 7.2 cannot reliably reconstruct the same validated bridge
resources for a second NVIDIA use in that boot. That completed remove event is
therefore recorded as a successful one-way detach, and a later add remains
driverless until reboot. A fresh physical hot-plug after an AMD-only graphical
startup has the same production recovery: boot again with the chain attached.

The guarded late ReBAR routine remains available as a development diagnostic,
but repeated end-to-end testing did not justify exposing physical hot-attach as
a supported tray action. Same-cable detach/reattach, where the USB4 cable never
leaves the enclosure, remains a separate validated transition.

## Failure behavior

All topology and resource checks happen before mutation. Once mutation begins,
any failure reaches the EXIT recovery trap, leaves NVIDIA blocked, records the
reboot requirement and restores the display manager. An interrupted operation
may resume only if the already-resized 16 GiB layout passes the dynamic verifier
and the exact HP-facing `pciehp` service can be quarantined.
